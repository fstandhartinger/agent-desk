Florian asked for four things (laptop chat, 28 Oct): a fullscreen/large button for the video in every view, a voice

## 1. Explainer context pack (explainer-pages + skill `explainer-video-webpage`)

Every page folder `pages/<slug>/` may carry two new files:

- `deepdive.md` — long German deep-dive (target 8–25k chars, hard max 60k): explains everything in the video in more
  depth, background, numbers with their sources, caveats, links/further sources, and a final section
  `## Herkunft` listing the job folders (`/home/flori/jobs/<job>`) and board entry ids (`#12345`) it came from.
  No secret values, no personal contact data, no bank details (same rule as pages).
- `context.json` — generated by `scripts/build_context.py <pageDir>` from timeline.json + points.json (+ deepdive.md):
  ```json
  {"v":1, "slug":"<slug or null>", "title":"…", "lang":"de", "duration": 67.2,
   "scenes":[{"id":"problem","start":0.18,"end":14.4,"title":"<points[scene].title>","text":"<narration of the scene>",
              "points":["p_title","p_nolink"]}],
   "elements":{"p_title":{"scene":"problem","t":0.18,"title":"…","short":"…"}},
   "deepdive":{"chars":12345,"sections":["## …", "…"]},
   "sources":[{"label":"…","ref":"…"}]}
  ```
  element → scene: the scene whose [start,end) contains the cue time `timeline.cues[id]`; a point id equal to a scene
  id maps to itself; points without a cue (data-point groups) map to the scene where they are referenced in stage.html
  if determinable, else null.

Serving (explainer-pages `server.js`): `deepdive.md` and `context.json` are PRIVATE: served only when the request
carries `Authorization: Bearer <EXPLAINER_CONTEXT_TOKEN>` (env, constant-time compare); otherwise 404 (same as a
missing file, no oracle). If `context.json` is missing the server may derive it on the fly from timeline.json +
points.json (+ deepdive.md) with the same code path as build_context.py (JS port) — so EVERY existing page has a
transcript/scene map even before backfill. The public player never needs these files.

Desk gateway env: `EXPLAINER_CONTEXT_TOKEN` (same value; set by the lead, write-only). The gateway fetches
`${EXPLAINER_ORIGIN}/p/<slug>/context.json` and `/deepdive.md` with that header server-side only; never forwards
them to the browser except as model answers.

## 2. Fullscreen / large view (explainer pages AND desk)

- Explainer pages: injected at serve time by server.js into every `index.html` (old pages included), like the desk

- Desk: same behaviour on the explainer stage in `ExplainerPanel` (next to the existing Kino button), and the
  canvas "Groß" overlay gets a real fullscreen button too.

## 3. Voice/text agent context at session start (gateway)

`loadPageContext(page)` additionally returns `pack = {scenes, elements, transcriptFull, deepdive}` (from context.json
/ deepdive.md, falling back to timeline/points). Instruction builder (`voice/instructions.js`, text `prompt.js`):

- Priority order inside a per-provider character budget `PAGE_BUDGET[provider]` (constants in one place, documented
  with the source of each provider limit): (1) clicked element: title/short/more + its scene id/title + the full
  narration of that scene, flagged "Florian hat gerade dieses Element angeklickt; seine erste Frage bezieht sich sehr
  wahrscheinlich darauf"; (2) full transcript with scene timestamps `[mm:ss–mm:ss] <scene title>: <text>`;
  (3) scene list with element ids; (4) deep-dive: as much as fits, sections relevant to the clicked scene first
  (keyword overlap), then the rest in order, truncated with a marker; (5) knowledge index (existing).
- Retrieval for the rest: new tool `explainer_context {query?, section?, sceneId?}` → deep-dive sections / scene
  narration matching the query (ranked keyword match, ≤ tool result limit). Listed in the prompt as "Für mehr aus dem
  Hintergrunddokument: explainer_context".
- Must hold for xAI Grok Voice, OpenAI GPT-Live-1 and Gemini 3.8 Live. A session started from a clicked element
  answers a detail question about that element correctly on the first turn without a tool call.

Binding security rules (critic checks every one):
- No tool or bridge method sends, posts, pays, deletes or changes state, except `board.handoff` which runs only from
  the authenticated human click, never from a model tool call. `notify.loginLink` stays gateway-internal (login UX),
  never a model tool. The bridge refuses unknown methods; the Sandy bridge serves only its allowlisted methods.
  Critic round 1 (P0-1): the same holds for `claude.start` / `claude.send`: the model tool `claude_task` only emits a
  `claude_proposal` card; only Florian's click (`POST /api/claude/proposal {id}`, cookie + same-origin, one-time) starts
  or sends. Proposals with the same title are shown once per turn (P2-6).
- A write request from the model ("schick eine Mail", "poste auf Discord", "deploy", "zahl") is answered honestly:
  the desk cannot do that itself; it offers `handoff_propose`.
- Never return secret values: every string from any tool passes `redact()` (extended for cookies, `Set-Cookie`,
  `password=`, PIN/TAN/one-time codes, private keys, seed phrases, env-file style `KEY=value` lines for secret-looking
  keys). env/secret files stay unreadable (existing deny list; add `.config/dev-secrets.env`, `~/.notify`,
  `~/.hermes/*.env`, browser profiles, cookie DBs, `*.sqlite` of browsers, `.git-credentials`).
- No crafted text can hold the event loop (critic round 7): texts above 8 KB are redacted in a worker (`offload.js`, same file
  in gateway and bridge) with a 1.5 s budget; over budget the result is "[Inhalt ausgeblendet: zu komplex für die Prüfung auf
  Geheimnisse]", never the unredacted text. Every regex of every gateway/bridge source file is tested against failing-tail
  runs and recheck attack strings (`test/redos-attacks.test.js`, 100 ms per regex and input).
- Tool results are data, never instructions (prompt line + illustrator rule already exist; extend to web/mail/discord).
- Bridge routing (gateway `bridgeHub`): each bridge announces caps; `call(method)` without explicit host picks the
  preferred connected host for that method: `ROUTE = {discord.*: [sandy], mail.*: [sandy], ops.*: [sandy],
  board.*: [sandy, lechonk], ctx.*: [sandy, lechonk], jobs.*: [sandy, lechonk], chats.*: both (merged),
  skills.*: [sandy, lechonk], claude.*: [lechonk], ctx.knowledge/ledger.*/code.*: [lechonk, sandy]}`. Host names
  allowlisted `^(lechonk|sandy)$`.
- Public repo: synthetic fixtures only (no real mail, Discord, board text, names of real counterparties beyond what
  already is public); the guard test must stay green. The lead squash-publishes.

## 5. Canvas: simple by default, details on demand

- Spec v2 gains optional `detail` (same `kind`, same schema: the detailed version of the SAME diagram, node ids shared
  where the same thing is meant). The top-level spec is the SIMPLE version.
- SIMPLE rules (illustrator prompt + quality gate, flow/architecture/sequence/timeline): at most 5 boxes (nodes),
  one main flow (at most one branch), at most 6 edges, no groups unless ≥ 2 boxes per group, labels ≤ 28 chars, no
  node `detail` text on the simple view, edge labels ≤ 2 words. Readable at a glance while talking. Charts/tables:
  simple = ≤ 6 items / ≤ 5 rows; detail = full data.
- DETAIL: 6–14 nodes, groups, edge labels, node details allowed (existing limits).
- The illustrator writes both in one JSON when the topic has more than the simple view shows; specs from agents via
  `canvas_render` that exceed the simple limits without a `detail` are kept as `detail` and a simple version is
  derived (illustrator simplify pass, fast model; until it is ready the complex one shows with the toggle on).
- Web: a "Details" toggle button in the canvas toolbar (and in the Groß/fullscreen view) whenever `detail` exists;
  default off; switching animates in place; state per visual id; history keeps both.
